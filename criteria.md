# Acceptance Criteria: FitFindr

Five criteria that define what working means for this agent, written in Unit 3 before evaluation results existed.

## 1. A matching query completes all three tools

Given a query that matches at least one listing, the agent completes all three tool calls and returns a fit card in at least 4 of 5 tries.

**Why this target:**

The search uses keyword overlap, so some valid user phrasing may not share enough words with a listing. I chose 4 of 5 because one search miss is possible even when the requested item exists.

## 2. An impossible query stops before the second tool

Given a query that matches no listings, the agent stops before calling `suggest_outfit` and returns a message naming what to change in 5 of 5 tries.

**Why this target:**

An empty search result is deterministic. The loop can directly check whether the result list is empty, so it should stop before the second tool every time.

## 3. The selected item stays consistent across state

For 5 of 5 successful matching queries, the ID stored in `session["selected_item"]` matches the item ID recorded when the item is passed to `suggest_outfit`.

**Why this target:**

The selected item is stored in session state before the outfit tool runs. This handoff is controlled by code rather than model output, so the same item should reach the next tool every time.

## 4. The fit card contains required listing information

For at least 4 of 5 successful matching queries, the fit card mentions the selected item's price and platform and contains between two and four sentences.

**Why this target:**

Price, platform, and length are observable requirements for the fit card. I chose 4 of 5 because the caption is generated by a model, so its exact wording and formatting can vary between runs.

## 5. Search respects the user's price ceiling

When a maximum price is supplied, every listing returned by `search_listings` has a price less than or equal to that maximum in 5 of 5 tries.

**Why this target:**

Price filtering is deterministic and happens before model generation. A listing above the user's stated budget should never be returned, so 5 of 5 is appropriate.
